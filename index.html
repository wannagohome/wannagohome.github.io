I moved OTA updates, which ship JS bundles straight to users without app store review, off a paid third-party service (EAS Update) and onto infrastructure I designed.

서버 프로그램 없이 S3와 CloudFront 엣지 함수로 동작하고, 어드민에서 기기 단위로 조금씩 배포하고 되돌릴 수 있습니다.

It runs on S3 and CloudFront edge functions with no server application, and the admin can roll out gradually device by device, or roll back.

Server-driven UI 구조 설계 및 개발 리드Led the design and development of server-driven UI

네이티브 앱은 UI 하나를 고치는 데도 앱 업데이트가 필요하고, 업데이트는 사용자에게 늦게 닿습니다. 그래서 서버가 내려 주는 데이터에 따라 UI를 자유롭게 바꿀 수 있는 구조를 만들었습니다.

In a native app, even a small UI change needs an app update, and updates reach users slowly. So I built an architecture that lets the UI change freely based on data sent by the server.

한 화면을 컴포넌트 단위로 쪼개고, 서버가 컴포넌트 정보를 내려 주면 앱은 그 정보대로 그립니다.

Each screen is split into components. The server sends the component data, and the app renders exactly that.

풀어야 했던 문제Problems to solve

성능과 코드 구조Performance and code structure
이전에 시도된 Server Driven UI는 성능이 느리고 코드 구조를 이해하기 어려웠습니다.An earlier attempt at server-driven UI was slow, and its code was hard to understand.
로직 없이 기능 구현Features without logic
앱은 서버가 준 데이터대로 그리기만 하므로, 뷰에 로직을 직접 넣지 않고 기능을 구현해야 했습니다.Since the app only renders what the server sends, features had to work without putting logic directly into views.
동적 범위 조절Scoping what is dynamic
네이티브 앱을 HTML처럼 전부 동적으로 그리기에는 리소스가 부족했습니다. 바꿀 수 있는 범위를 적정 수준으로 제한하면서도 범용성을 지켜야 했습니다.There weren’t enough resources to make a native app fully dynamic like HTML. The changeable scope had to be limited to a sensible level while staying general-purpose.

Tuist를 활용한 프로젝트 구조 및 성능 향상Improved project structure and performance using Tuist

빌드 시간이 너무 오래 걸렸고, 함께 일하는 사람은 늘어나는데 프로젝트는 그만큼 확장하기 어려웠습니다. 프로젝트 파일에서는 충돌도 자주 났습니다.

Builds took far too long, and while the team kept growing, the project couldn’t scale with it. Project files also caused frequent conflicts.

Tuist를 적용해 프로젝트 구조를 바꿨습니다. 적용 과정은 요기요 기술 블로그에 정리했습니다.

I restructured the project with Tuist and wrote up the process on the Yogiyo tech blog.

로그 데이터 전송 효율화 설계Designed more efficient log data transmission

로그를 이벤트가 생길 때마다 하나씩 보내다 보니, 기기 한 대가 1초에 약 10번 요청을 보내 트래픽이 과도했습니다.

Logs were sent one by one as each event occurred, so a single device made about 10 requests per second, creating excessive traffic.

여러 로그를 묶어 보내 트래픽을 줄이고, 바로 보내지 않는 동안 로그가 사라지지 않도록 스토리지에도 캐싱했습니다.

I batched logs to cut the traffic, and cached them in storage too so they wouldn’t be lost while waiting to be sent.
